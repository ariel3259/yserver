# VRR (adaptive sync), one output in direct scanout — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** a CRTC runs with `VRR_ENABLED` = 1 exactly while its output is VRR-capable and the direct-scanout
transaction being committed belongs to a client window; cursor motion does not drive the refresh rate meanwhile.

**Architecture:** no new commit and no new timer. Each vsync frame commit decides the value it wants (direct frame of
an `Unredirected` owner → 1, every other frame → 0) and carries `VRR_ENABLED` only when that differs from what the
kernel holds. The value rides the frame builders that already carry the pending gamma LUT, and reuses gamma's EINVAL
retry and latch. The commits that turn outputs off carry the clear before the device is given up. A cursor position
pending on a VRR CRTC waits up to 33 ms for a direct frame, with the deadline stored on the pending move itself.

**Tech Stack:** Rust, drm-rs atomic, existing yserver test harness (recording atomic executor, controlled clock).

**Spec:** `docs/superpowers/specs/2026-10-23-vrr-design.md`

## Decisions taken while planning (rulings on the spec's open items)

1. **No "pending VRR" storage.** Gamma needs a pending slot because a ramp is a value waiting to be sent. VRR's wanted
   value is a function of the commit being built, so each frame builder compares it with the committed value. Only
   *capable*, *committed* and the EINVAL latch are stored.
2. **Gamma first.** A commit carries at most one of the two optional CRTC changes. When a gamma LUT is pending, the
   frame carries the LUT only and the VRR change goes out with the next frame. This keeps gamma's one-retry EINVAL
   attribution exact; a frame of delay on VRR entry or exit is invisible.
3. **Release clear rides the off commits.** VT release, DPMS off and shutdown already send one commit per CRTC
   (`disable_output`) or per device (`disable_all_outputs_on_device`). Those commits carry `VRR_ENABLED` = 0 instead of a
   standalone commit; this also settles the spec's question about a primary-plane flip. If the off commit is rejected
   with the property, it is retried once without it.
4. **Cursor deadline lives on the pending move.** The entry in `atomic_pending_moves` carries an optional deadline. Every
   site that consumes or clears a pending move drops the deadline with it, so a stale deadline cannot exist. A new
   position for the same CRTC replaces the position and keeps the deadline. The deadline is set by the first
   scheduling pass that holds the move back, using the backend clock (`monotonic_now`).
5. **The tearing `deferred_cursor_wake` stays separate.** It caps software-cursor composition with its own reset rules.
   Sharing it would couple two policies; the VRR deadline needs no new field outside the pending move.

## Review Focus

1. A cursor move arrives just after a direct frame carried the previous one: it must get its own fresh 33 ms deadline,
   not an expired one (Task 4, `vrr_cursor_new_move_after_carried_move_gets_fresh_deadline`).
2. A compositing manager that unredirects a fullscreen game, then redirects it again: `vrr on` then `vrr off`, never
   VRR while the COW owns direct (Task 2, `vrr_cow_owner_never_enables`, `vrr_unflip_clears`).
3. An output replaced by a RandR modeset on the same CRTC keeps the committed value and the latch; on a different CRTC
   both start fresh (Task 1, `vrr_state_survives_output_replacement_on_same_crtc`).
4. Tearing on: async direct flips never carry `VRR_ENABLED`; the first vsync commit does (Task 2,
   `vrr_async_flip_defers_to_next_vsync_commit`).
5. DPMS off then on with VRR on: the off commit clears it, and the next direct frame turns it back on (Task 3,
   `vrr_dpms_off_clears_and_direct_frame_reenables`).

  `vrr_committed` is true and the pending move has no deadline, set `now + VRR_CURSOR_DEADLINE` and return without a
  commit; with a deadline in the future, return without a commit; at or past it, send as today.

  under the same conditions as `has_eligible_atomic_cursor_move` (not in flight, not in `cursor_retry_waits_for_flip`,
  not in hide recovery, available and HW-bound); chained into `backend_scanout_next_wakeup` under `allow_kms_timers`,
  like `gamma_deadline`. A move waiting for a flip after an EBUSY keeps its deadline but reports none until the
  matching flip event clears the wait.
