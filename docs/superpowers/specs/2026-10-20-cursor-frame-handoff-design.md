## Problem and current behavior

P2 moves the cursor image, hotspot, attach and detach onto the per-CRTC atomic stream and protects sprite buffers with accepted-state ownership and event-attributed leases. It still submits those four kinds of change as separate cursor-only commits outside the primary frame. Shared, copied, direct and composed-unflip frames continue to carry only the applied cursor position. The scene records `ShowOnRetire` and `HideOnRetire` (P2 names, may change) operations with the pending frame; when its page-flip retires, the scene uploads/shows/hides the cursor separately and only then publishes the new software/hardware mode. The transition therefore belongs to retirement rather than to the frame that made the transition necessary. These are the P2 behaviors described by P2 R20 and in the current worktree's [status entry](../../status.md).

The NVIDIA cursor jump is a concrete stale-state replay. The reference status records the #244 reproduction against master `9524c80d`: window entry captures pointer P0=(120,80); motion advances to P1=(180,130) while a copied frame is outstanding; after the frame, its stored transition issues a cursor operation at P0, adjusted by the new cursor's (7,9) hotspot to (113,71). The reference regression exercises motion both before frame acceptance and after acceptance but before retirement, and requires every accepted post-motion position to use P1, never P0 (`docs/status.md`, 2026-10-17 atomic-cursor entry; `round_b_jump.rs`).

P2 also has a measured cost on NVIDIA RTX 5060 Ti: with an animated cursor over held direct scanout, each animation image change attempts a cursor-only commit while the direct frame owns the CRTC slot. The resulting EBUSY/deferred show is treated as a hook failure and requests an unflip. The P2 validation note records 76 such unflips in about 26 seconds, with no dropped client frames in that run; the current status summarizes this as one unflip per animation frame. P3 must keep direct scanout held through cursor animation and stop those cursor-triggered unflips. Evidence: current `docs/status.md`, the P2 validation record [`plans/2026-10-20-cursor-sprite-state-validation.md`](../plans/2026-10-20-cursor-sprite-state-validation.md), and reference status.

P3 makes each submitted primary frame own the cursor state that becomes visible with it. A successful acceptance publishes that frame's cursor ownership. Its attributed completion retires the prior primary and sprite ownership, but does not start another cursor transaction or replay coordinates captured by an older scene request.

## P2 and P1 dependency contract

P2 supplies the stable cursor-state behavior this change builds on: the accepted-state diff in R16; the sprite reservation and acceptance boundary in R13; replacement-lease release in R10; event attribution in R11; one in-flight commit per CRTC in R12; deferred upload behavior in R19 and R21; and the cursor-field tagging and async restriction in R17. P1 supplies accepted kernel commit IDs and exact event matching in R1–R5, plus shared/copied/direct/unflip event propagation in R9–R12.

P3 extends P2 R10/R11 so a frame commit that replaces a cursor binding can release its prior lease on that frame's matched event. P3 supersedes P2 R20's position-only restriction for synchronous primary-frame submissions: those submissions may carry the cursor state delta owned by that frame. P2's diff, acceptance, reservation, lifetime and fallback contracts remain in force. Async/tearing requests remain cursor-property-free as required by P2 R17; P3 does not alter async qualification.

## Terms

- **Frame cursor plan:** the logical cursor assignment and primary cursor content associated with one output frame. It identifies the selected sprite and hotspot when hardware cursor ownership is requested. The pointer position is sampled at final submission as required by R3 below.
- **Accepted frame:** a primary submission accepted by KMS. For a copied route, render completion alone is not acceptance; acceptance occurs only when the copied primary and its cursor delta are submitted to KMS.
- **Cursor receipt:** the platform-neutral result of an accepted frame, identifying the accepted cursor mode and whether its primary contains a software cursor. It is not a kernel event ID; P1's commit ID remains a separate identity.
- **Cursor-only commit:** a cursor request with no primary framebuffer update. It remains available when no primary frame is pending, especially for pointer motion on an otherwise static screen and cursor changes while a direct primary is held without a successor.

## Rules

### Frame ownership and acceptance

**R1 — Every output frame has an explicit cursor plan.** Each submitted shared, copied, direct or composed-unflip primary has an output-local frame identity and a plan for Hardware, Software or Hidden cursor ownership. The plan identifies the software-cursor pixels and position when those pixels are part of the primary; a hardware-owned or hidden primary is recorded as cursorless. The same plan follows a copied render job until its final KMS submission. A render job ID is never treated as KMS acceptance or as a cursor-frame identity. Test: inspect accepted receipts for all routes and assert the recorded primary content matches the cursor pixels actually submitted.

**R2 — A synchronous primary and its cursor transition are one atomic update.** On the P2 atomic path, a shared scene frame, copied final submission, direct scanout frame or composed unflip carries the full P2 R16 cursor delta needed for that frame on the same atomic request as the primary. This includes attach, detach, sprite/hotspot replacement and position where those differ from accepted state. A software-cursor primary becomes visible in the same accepted frame that detaches hardware; a hardware-cursor primary is cursorless and attaches/replaces the plane in that frame. No second cursor-only image/show/hide commit is generated for that transition. Test: record KMS properties and assert one accepted primary commit includes both the expected primary and cursor fields, with no follow-up cursor transition at retirement.

**R3 — Hardware position is sampled at final submission.** Do not submit a position captured when the scene request or copied render job was created. Immediately before building the final KMS request, read the current effective pointer position and the applicable hotspot, transform to that output's CRTC coordinates, and prepare the frame's position delta. For copied frames, do this after copy/render readiness, at the sink's KMS submit boundary. A frame's image/visibility assignment remains the one owned by its plan; motion while it waits updates the sampled position, not a saved earlier coordinate. Test both P0/P1 schedules from the jump reproduction and assert no accepted post-motion request restores P0.

**R4 — Only acceptance publishes frame ownership.** Before a request is accepted, its frame plan and sprite reservation are staged only; the frame has not changed the accepted cursor mode or binding. Once KMS accepts the primary-plus-cursor request, publish the accepted frame state and return its receipt. A copied render completion, failed ioctl, unavailable slot, or canceled frame publishes no frame receipt. Keep P2's existing R14 rejection policy in force: if its attribution path performs a separate blocking detach, settle that outcome under R14 rather than treating the rejected frame as accepted. Test that pre-acceptance stages publish no receipt and that both ordinary rejection and the existing R14 detach outcome match their respective accepted-state rules.

**R5 — Retirement does not perform a cursor transition.** A page-flip completion retires the primary frame and settles its receipt, software-cursor damage bookkeeping and resources. It performs no cursor upload, show, hide, move, attach, detach, or replay of a frame-captured position. An older frame's retirement cannot overwrite a newer accepted cursor mode. Test by recording all cursor-affecting requests from acceptance through retirement and asserting the event adds no cursor request and does not change the newest accepted receipt.

**R6 — Staged sprite reservations have one outcome.** Reserve a sprite before submitting a frame that will use it. On successful acceptance, transfer the reservation to P2 accepted ownership. If frame preparation, rendering, copying, output validation or KMS submission is canceled or fails before acceptance, release that frame's reservation exactly once. A failed request does not transfer the frame's reservation; if P2 R14 then performs a separate blocking detach, settle the prior accepted lease exactly as R14 requires. A staged sprite is never reused while reserved. Test cancellation before copy completion, no-BO/unavailable handoff, and failed shared/copied/direct submission; assert no reservation or framebuffer ownership leaks.

**R7 — Multi-output state is consistent and independently accepted.** Derive each output's cursor image, visibility and logical pointer position from the current effective cursor state. Convert position using that output's origin and hotspot. Each output publishes a receipt only after its own primary request is accepted; a grouped request's P1 commit ID is attributed to each target CRTC as P1 specifies. One output's acceptance or retirement cannot claim, release or roll back another output's lease. If outputs accept at different times, each retains truthful per-CRTC state until its own replacing event. Test cursor movement across two outputs, grouped direct and composed-unflip replacement, and a delayed/canceled peer output; assert correct local coordinates, visibility, frame receipts and per-output lease counts.

**R8 — A frame pending on a CRTC owns its cursor transition.** If a primary frame is being submitted for an output, attach/detach, image/hotspot change, and the frame's pointer position travel with that primary. Do not spend a separate cursor-only commit slot for state the frame can carry. A cursor-only request already in flight follows P2 R12: the primary waits for its attributed event; it does not publish the frame's cursor ownership early. Test a frame arriving behind a cursor-only commit and assert exact order, no overlapping request, and no premature receipt.

### Cursor-only work and direct scanout

**R9 — Cursor-only updates remain when no primary can carry them.** Pure pointer motion on a static output remains cursor-only when no primary frame is pending; it must not force a software composition. A held direct primary with no successor likewise continues to service cursor changes through the cursor-only lane. If that lane must wait behind an accepted CRTC commit, keep the newest intent for its next valid opportunity; a deferred/EBUSY cursor update by itself must not request an unflip. Test static-screen motion produces no scene composition, and held-direct image, hotspot, show, hide, animation and first-bind changes do not unflip or drop client frames.

**R10 — Direct and unflip primaries carry their own cursor content.** A direct successor that changes cursor ownership carries the delta on the accepted direct request. A composed unflip whose primary contains a software cursor carries the matching hardware detach in that same request. A held direct frame without a successor keeps using cursor-only updates under R9; animation alone is not an unflip reason. Test direct entry, held-direct animation, transition to composed software cursor, and retirement of both direct and unflip frames, checking primary pixels and cursor properties together.

**R11 — Commit identity and lease release follow the replacing frame.** Every event-producing frame commit uses the accepted P1 kernel commit ID associated with its target CRTC(s); a render completion ID or frame identity is not a substitute. An explicit unmatched, duplicate, stale, wrong-device or wrong-CRTC event retires nothing under P1 R3/R5. The prior sprite lease is released only by the event attributed to the accepted commit that replaced that lease, per P2 R10/R11. Acceptance does not free the old sprite, and cancellation creates no event obligation. Test by withholding the replacement event, delivering wrong and duplicate IDs, then the accepted ID; assert the old lease survives until only the final event.

**R12 — Shared frame interfaces stay platform-neutral.** `yserver-render` may carry frame identity, cursor assignment, primary-content metadata and a receipt, but no DRM, GBM or KMS types. Native surface adapters in `surface/platform.rs` and `surface/swapchain.rs` implement the same handoff with no KMS event identity and preserve their existing cursor behavior. Test a surface frame through acceptance and retirement, checking no KMS dependency and no extra cursor operation.

**R13 — X clients retain Xorg/master semantics.** P3 does not change XFIXES hide/show state, `GetCursorImage` pixels or hotspot, pointer position, cursor-resource selection, or visibility decisions. At every presented frame the user sees the cursor image, hotspot and visibility selected by the core, with no stale-coordinate jump, cursor ghost, duplicate software-plus-hardware cursor, or retirement-time blink. The timing of a transition can change: when a primary frame is pending, its cursor transition becomes visible at that frame's atomic latch instead of as a separate cursor commit triggered after retirement. Pure motion with no pending frame remains cursor-only. This frame-coupled timing is the intended visible scheduling difference; tests and hardware validation must confirm that it preserves Xorg/master behavior and does not add a lost-frame symptom.

## P3 ownership boundary

| Area | P3 responsibility |
|---|---|
| `yserver-render` scene frame state | Add frame identity, assignment, accepted receipt and primary-cursor content; remove stored retire-time cursor operations from scene/tick/flip/lifecycle/damage bookkeeping. Retirement settles the accepted frame only. |
| Platform frame ownership | Stage, reserve, cancel and accept per-frame cursor ownership. `CursorFramePlan.hardware_only` and `cursor_frame_updates_for_submit` are reference implementation names for distinguishing a cursorless primary from live hardware cursor state and sampling at the final copied submit; they are not behavioral dependencies of this spec. |
| Primary submitters | Integrate frame receipts and cursor deltas in shared/copy sink submission, direct successor scanout and composed unflip. Preserve P1 accepted-event plumbing and P2 accepted-state/lease rules. |
| Pointer and cursor producers | Feed the current effective sprite, visibility and pointer into frame-owned updates; held-direct show/hide/animation/first-bind remains available without forcing an unflip. |
| Surface adapters | Adapt the shared frame interface in `surface/{platform,swapchain}.rs` without introducing KMS types into the renderer. |
| Tests | Add the jump, frame-ownership, cancellation, late-sampling, producer, held-direct and cross-output cases. `with_copied_route` is a P3 test-fixture helper proposed by the inventory for copied-route setup, not a production API. |

## Non-goals

- AMD scheduling suppression, one-attempt-per-pass gates, persistent retry eligibility and the `scanout.rs` deadline-spin finding (P4).
- Rejection-recovery keys; changes to EBUSY/EINVAL attribution; CRTC plane reassignment; quarantine; recovery-specific cursorless retry/recompose policy; legacy executor/fallback removal; the `check-layout.sh` cursor guard (P5).
- VRR, async/tearing qualification changes, or cursor properties on async commits.
- New cursor protocol behavior, changes to XFIXES or `GetCursorImage`, sprite-pool redesign, P2 capability/eligibility changes, P1 event-identity changes, or lifecycle policy beyond canceling staged frame reservations safely.

## Test requirements

**A — End state.** Every stateful case asserts both intermediate ownership and final normal-completion state. Before the replacing event, the prior sprite lease remains owned; after the exact P1 event, that prior lease is released. At completion there is no pending primary/event association, copied render job, frame receipt awaiting retirement, staged cursor reservation, accepted cursor user without an owner, or live cursor allocation after pool teardown. Canceled frames leave no receipt or event obligation. Do not clear ownership maps or destroy a fixture to manufacture a settled result.

**B — Backend-driven production paths.** Install the recording atomic executor, sprite-buffer ledger, P1 device-qualified event injector and required topology, then advance through `Backend` entries or `core_loop::run_core` (including composition, direct Present, copied render completion, page-flip readiness, cursor requests and output state). Do not call internal submit/accept/retire or lease methods to simulate a production path. Pure scene-plan, receipt and request-diff boundary tests may call pure functions directly, clearly label that boundary, and do not replace Backend coverage.

Required backend scenarios cover shared and copied frames; direct successors and composed unflips; pointer motion before acceptance and after acceptance but before retirement; software↔hardware and hidden transitions; cancellation and submit failure; late copied-route sampling; cross-output cursor movement and delayed peer acceptance; held-direct image/hotspot/show/hide/animation/first bind; cursor-only motion with no pending frame; and old/wrong/duplicate versus accepted P1 event IDs. Every planned test names a production mutation that makes its intended assertion fail, not merely a compile or timeout failure.

**C — Hardware.** Validate on AMD Raphael and NVIDIA RTX 5060 Ti, comparing against master/P2 with the same workloads. On NVIDIA, explicitly reproduce the P0=(120,80) → P1=(180,130) cursor-jump schedule across window entry while a copied frame waits, and verify no accepted post-motion cursor operation restores P0. Also animate over fullscreen held direct scanout and require zero cursor-triggered unflips during the isolated interval, continued direct scanout, and no client-frame loss; the P2 reference case produced 76 EBUSY-triggered unflips in about 26 seconds. Run the corresponding cursor/frame benchmark on AMD and record executed versus unavailable cases. Existing validation reports that mpv's linear buffer is rejected by `add_fb2` on AMD, so lack of an AMD direct path must be reported as such rather than counted as direct-scanout coverage. This is a later validation task; no hardware is accessed while writing this spec.

**F — Repetition, load and skips.** Run each new test five times under 16 concurrent CPU busy loops; run GPU-waiting cases 20 times under the same load. Each fixture skip prints exactly one line naming its reason, emitted by the constructor that decides the skip. Report executed and skipped cases separately. Keep copied/SYNC_FD or driver-capability skips distinct from passing results.

## Open questions for the user

1. **Multi-output partial acceptance:** should one output's accepted receipt wait for every peer output in a logical scene update? **Recommended default:** no; publish per CRTC only after that CRTC's accepted request, retain its prior lease until its own P1 event, and cancel only unaccepted peer reservations. This matches P1's event scope and P2's per-CRTC ownership.
2. **AMD direct-scanout coverage:** should P3 require a separate AMD client if the standard mpv workload still cannot reach direct scanout? **Recommended default:** require AMD frame/cursor validation and the NVIDIA direct/unflip case; add an AMD direct client when available, and report the existing `add_fb2` limitation as uncovered until then.
3. **Cursor timing threshold:** should P3 add a numeric motion-to-visible ceiling for frame-coupled transitions? **Recommended default:** no new latency threshold in P3; require the Xorg/master visual and protocol parity above, preserve cursor-only motion when no frame is pending, and report measured frame cadence/latency for review.
