## Problem and current behavior

P2 moves the cursor image, hotspot, attach and detach onto the per-CRTC atomic stream and protects sprite buffers with accepted-state ownership and event-attributed leases. It still submits those four kinds of change as separate cursor-only commits outside the primary frame. Shared, copied, direct and composed-unflip frames continue to carry only the applied cursor position. The scene records `ShowOnRetire`/`HideOnRetire` (P2 name, may change) operations with the pending frame; when its page-flip retires, the scene uploads/shows/hides the cursor separately and only then publishes the new software/hardware mode. The transition therefore belongs to retirement rather than to the frame that made the transition necessary. These are the P2 behaviors described by P2 R20 and in the current worktree's [status entry](../../status.md).

The NVIDIA cursor jump is a concrete stale-state replay. The reference status records the #244 reproduction against master `9524c80d`: window entry captures pointer P0=(120,80); motion advances to P1=(180,130) while a copied frame is outstanding; after the frame, its stored transition issues a cursor operation at P0, adjusted by the new cursor's (7,9) hotspot to (113,71). The reference regression exercises motion both before frame acceptance and after acceptance but before retirement, and requires every accepted post-motion position to use P1, never P0 (`docs/status.md`, 2026-10-17 atomic-cursor entry; `round_b_jump.rs`).

P2 also has a measured cost on NVIDIA RTX 5060 Ti: with an animated cursor over held direct scanout, each animation image change attempts a cursor-only commit while the direct frame owns the CRTC slot. The resulting EBUSY/deferred show is treated as a hook failure and requests an unflip. The P2 validation note records 76 such unflips in about 26 seconds, with no dropped client frames in that run; the current status summarizes this as one unflip per animation frame. P3 must preserve direct scanout for eligible synchronous hardware-cursor updates and prevent cursor-only deferral alone from requesting an unflip. Evidence: current `docs/status.md`, the P2 validation record [`plans/2026-10-20-cursor-sprite-state-validation.md`](../plans/2026-10-20-cursor-sprite-state-validation.md), and reference status.

Issue #279 (maintainer report, dual-output RX 6800) shows the retirement coupling breaking animated cursors: Xcursor theme animations such as `xsetroot -cursor_name watch` and the MATE busy cursor blink on master before P2 and stay invisible with P2. `ShowOnRetire` binds only when the scene's live cursor entry still has the exact record version that was composed; a newer animation frame is registered before almost every flip retires, so the version mismatches, P2's no-stale-bytes rule hides the plane, the cursor resolves to Hidden and the next frame repeats the race (`retire-time upload (vN) — no matching entry bytes` about 60 times a second, no successful show). Static cursors never change version between compose and retire. The P2 hardware validation missed this because its animation probe changed frames every 300 ms, slower than any flip retirement, so the versions always matched; theme animations at their own frame delays were not exercised. The issue cites Xorg's animated-cursor behavior (frame 0 shown immediately, each later frame loaded by a timer as an ordinary cursor, no frame dependent on a compose retiring) from its report; that source was not read for this spec.

P3 makes each submitted primary frame own the cursor state that becomes visible with it. A successful acceptance publishes that frame's cursor ownership. Its attributed completion retires the prior primary and sprite ownership and does not itself perform another cursor transaction or replay coordinates captured by an older scene request; it may wake independent work for newer retained intent under R5/R9.

## Terms

- **Frame cursor plan:** the logical cursor assignment and primary cursor content associated with one output frame. It identifies the selected sprite and hotspot when hardware cursor ownership is requested. The pointer position is sampled at final submission as required by R3 below.
- **Accepted frame:** a primary submission accepted by KMS. For a copied route, render completion alone is not acceptance; acceptance occurs only when the copied primary and its cursor delta are submitted to KMS.
- **Cursor receipt:** the platform-neutral result of an accepted frame, identifying the accepted cursor mode and whether its primary contains a software cursor. It is not a kernel event ID; P1's commit ID remains a separate identity.
- **Cursor-only commit:** a cursor request with no primary framebuffer update. Subject to R9's accepted-primary eligibility, it remains available when no primary frame is pending, especially for pointer motion on an otherwise static screen and cursor changes while a direct primary is held without a successor.

## Rules

### Frame ownership and acceptance

**R1 — Every output frame has an explicit cursor plan.** Each submitted shared, copied, direct or composed-unflip primary has an output-local frame identity and a plan for Hardware, Software or Hidden cursor ownership. The plan identifies the exact software-cursor pixels and position when those pixels are part of the primary; a hardware-owned or hidden primary is recorded as cursorless. The same plan follows a copied render job until its final KMS submission. A render-job ID is never treated as KMS acceptance or as a cursor-frame identity. A receipt describes the primary's actual cursor pixels/properties, not only its desired mode. Test: compare accepted receipts, primary pixels and cursor properties on every route, including an unflip that reuses a retained framebuffer.

**R2 — An Atomic primary and its cursor transition are one atomic update.** On a device using the P2 Atomic path, each shared scene frame, copied final submission, direct successor or composed unflip carries the complete P2 R16 cursor delta appropriate to that frame's actual primary content and ownership on the same atomic request as the primary. This includes attach, detach, sprite/hotspot replacement and position where those differ from accepted state. A software-cursor primary may detach hardware in that request only when its submitted pixels actually contain that software cursor. A cursorless hardware-owned primary attaches/replaces the plane in that frame. No second cursor-only image/show/hide commit is generated for a transition owned by that Atomic frame. Legacy devices use the safe handoff adapter required by R5 until its replacement is designed. Test Atomic acceptance and actual primary pixels/properties on shared, copied and direct routes; test Legacy handoff separately.

**R3 — Frame content and hardware intent have different sampling rules.** Software-cursor pixels, their image and hotspot, visibility and position are an immutable snapshot of what was rendered into that primary. For a cursorless primary on an already-steady Hardware path, sample the current complete hardware intent—effective image, hotspot, visibility and pointer position—immediately before building the final KMS request, transform position to that output's CRTC coordinates, and prepare the delta then. This includes rebuilding when the initially prepared delta was empty. For copied frames, final sampling occurs after copy/render readiness at the KMS submit boundary. The pointer POSITION of every hardware-bearing frame update — including an ownership-changing plan such as a first attach from Software or Hidden — is sampled at that same final-submission boundary, with the frame's own sprite and hotspot; no hardware-bearing request ever carries a position captured at staging. An ownership-changing plan otherwise remains owned by its frame (its sprite, hotspot and visibility do not change at final submission); later image/visibility observations stay retained for reconciliation after that plan's acceptance or rejection and cannot be cleared by its completion. Test both P0/P1 schedules, a copied first attach from Software and from Hidden with motion after staging but before acceptance (the accepted attach must carry P1, never P0), changes to image/hotspot/visibility while a cursorless copied primary waits, and an initially empty delta followed by motion; assert actual software pixels remain the rendered snapshot and no accepted hardware update restores stale intent.

**R4 — Only acceptance publishes frame ownership.** Before a request is accepted, its frame plan and sprite reservation are staged only; the frame has not changed the accepted cursor mode or binding. Once KMS accepts the primary-plus-cursor request, publish the accepted frame state and return its receipt. Kernel acceptance is irreversible for ownership accounting: a later bookkeeping error is settled as an accepted request and must not cancel/release its storage as if submission failed. A copied render completion, failed ioctl, unavailable slot, skipped frame, or canceled frame publishes no frame receipt and cannot donate its ownership-changing intent to the cursor-only lane. Keep P2's R14 rejection policy in force: a separate successful blocking detach settles under R14 rather than making the rejected frame accepted; failed detach retains prior ownership. Test pre-acceptance stages, ordinary rejection, accepted-then-settlement-fault injection at the transaction boundary, and both detach outcomes.

**R5 — Atomic retirement settles ownership; Legacy keeps a safe adapter.** On the Atomic path, page-flip completion retires the primary frame and settles its receipt, software-cursor damage bookkeeping and resources; the completion itself performs no cursor upload, show, hide, move, attach, detach or replay of frame-captured state. It may wake/re-evaluate the cursor-only scheduler after releasing a blocker. Any subsequent transaction must be independently derived from the newest retained intent, never from the retired receipt; with no newer intent retirement causes no cursor I/O. Until a replacement is designed in P5, Legacy devices retain a safe adapter that applies their retirement-time transition and preserves established behavior, with one required change under R14: a superseded show never hides the plane. Test separately: Atomic no-new-intent retirement adds no I/O; when newer intent exists, the independent follow-up uses only that latest intent; Legacy transition remains safe. Do not assert that all cursor I/O after every completion is forbidden.

**R6 — A staging pin does not create a duplicate accepted binding user.** A staged reservation protects sprite storage until acceptance or rejection. Acceptance creates a new accepted user only when the frame acquires a different binding. A same-binding move, invalid-state rebind, or empty delta retains exactly the one existing accepted user; release any extra staging pin instead of converting it into another user. When a genuinely new binding is accepted, transfer its reservation to one accepted user and retain the replaced binding under P2 R10/R11 until its matching event or a successful blocking detach/all-off cleanup releases it. On pre-acceptance cancellation or failure, release each staged pin once. Test `A → A → B`, same-binding movement, invalid-state rebind, empty delta, grouped partial preparation rollback, cancellation before copied completion and failed submissions; assert exact prepared/accepted counts and eventual pool reuse.

**R7 — Multi-output state is consistent and published per CRTC.** Derive each output's cursor intent from the current effective state, convert position using that output's origin and hotspot, and publish a receipt only for a CRTC whose primary request was accepted. One grouped ioctl accepts all of its target CRTCs together; their page-flip events retire independently. Separate submissions have no peer barrier: one CRTC's acceptance, retirement or cancellation never claims, releases or rolls back another's lease. Each output keeps truthful per-CRTC state until its own replacing event. Test cross-output movement, grouped direct/composed-unflip acceptance with independent retirement, separate submissions with a blocked peer, and a delayed/canceled peer; assert local coordinates, visibility, receipts and lease counts.

**R8 — A frame pending on a CRTC owns its mode transition.** Attach/detach and other ownership-changing state for an output's pending primary belongs to that primary; a cursor-only request cannot take over a transition from a skipped, rejected or canceled frame. If a cursor-only request is already in flight, the primary waits for its attributed event under P2 R12 and does not publish frame ownership early. Non-mode hardware intent may be reconciled only under R3/R9. Test cursor-before-primary ordering, a competing pending transition, and rejected/skipped/canceled frame intent; assert no cursor-only transaction steals that transition and the future primary carries it.

### Cursor-only work and direct scanout

**R9 — Cursor-only work requires eligible accepted primary content and retained progress.** Hardware cursor-only attach/show is eligible only over an accepted cursorless primary and when no competing frame-owned mode transition is pending. A skipped, rejected or canceled frame cannot authorize it. If the accepted primary contains software-cursor pixels, changing visibility or pixels requires a new software-bearing primary; a cursor-only hardware attach must not place a second cursor over those pixels. Pure hardware pointer motion on a static cursorless primary and cursor changes over a held direct cursorless primary with no successor remain cursor-only and do not force composition.

Retain the newest complete intent—image, hotspot, show/hide and position—while a CRTC commit, unavailable sprite storage or another eligible blocker prevents submission. A progress source must retry it when the blocker clears, without requiring another Present or pointer motion. A cursor-only acceptance publishes the new accepted cursor state but creates no primary frame receipt and does not alter the accepted primary's recorded pixels. A deferred/EBUSY cursor update alone does not request an unflip for a qualified synchronous hardware-cursor case; actual hardware failure and ineligible cases may still require composition. Test both stationary direct scanout with no successor and a streaming direct workload; assert accepted, visibly progressing cursor changes, unchanged primary continuity, reasoned unflip counts and no client-frame loss in the qualified case.

**R10 — Direct and unflip receipts describe the framebuffer's actual cursor pixels.** A direct successor that changes cursor ownership carries the delta on the accepted direct request. A composed unflip targeting Software may detach hardware in the same request only if its submitted primary actually contains the software cursor. P2's composed-unflip path can submit retained compositor framebuffers without rendering a new software cursor into them; for that case keep the hardware cursor attached through the cursorless unflip and detach only with the subsequent real software-bearing primary. A transition to Hidden may detach with cursorless pixels when the accepted receipt records Hidden. Desired Software mode by itself never authorizes detach. A held direct frame without a successor uses R9; animation alone is not an unflip reason for a qualified synchronous hardware-cursor case. Visible cursors during tearing, oversized cursors and actual hardware failure remain legitimate composition/unflip causes. Test the real retained-buffer unflip, verify its pixel contents and properties, and assert hardware remains until software pixels and detach arrive together.

**R11 — Commit identity and lease release follow the replacing frame, with blocking-cleanup exceptions.** Every event-producing frame commit uses the accepted P1 kernel commit ID associated with its target CRTC(s); a render completion ID or frame identity is not a substitute. An explicit unmatched, duplicate, stale, wrong-device or wrong-CRTC event retires nothing under P1 R3/R5. The prior sprite lease remains owned until the matching event for its replacing commit, except that a successful P2 R14/R22 blocking detach or R23 all-off cleanup may settle it without that event. A failed detach retains ownership. Acceptance alone never frees the prior sprite, and cancellation creates no event obligation. Test withheld, wrong and duplicate events followed by the accepted ID, plus successful and failed blocking detach and all-off cleanup; assert exact ownership and event obligations.

**R12 — Shared frame interfaces stay platform-neutral and preserve native/rootless behavior.** `yserver-render` may carry frame identity, cursor assignment, primary-content metadata and a receipt, but no DRM, GBM or KMS types. Native surface frames use the same handoff without KMS event identity; the current swapchain adapter path is `surface/swapchain/mod.rs` (P2 name, may change). Preserve rootless cursor publication when cursor state changes without any output frame: the shell still receives the effective sprite, hotspot and hidden/shown state. Test native acceptance/retirement with no extra cursor operation and rootless define, hide/show and animation changes without output frames.

**R13 — X protocol behavior is preserved; frame-coupled visibility is an observable scheduling difference.** Receipts do not change logical cursor selection, image/serial/hotspot replies, hide counts, notifications, pointer coordinates or Present semantics. These protocol results remain independent of scanout acceptance, as in the current cursor-image request path (P2 name, may change). Physical cursor timing relative to presented content is observable and cannot be promised identical: an immutable delayed software frame may show the cursor snapshot captured when it was rendered even if the core has selected a newer cursor by latch time. Hardware intent for cursorless steady-Hardware frames follows R3. Require no stale-coordinate jump, ghost, duplicate software-plus-hardware cursor or retirement-time blink, and require the newest eligible intent to make visible progress without another client Present or pointer motion. Tests separate protocol parity from the observable frame-coupled schedule and verify eventual presentation progress; they do not require the currently selected core image to appear in every already-rendered frame.

### Animated cursors (issue #279)

**R14 — A newer cursor image never makes a visible hardware cursor disappear.** An image change registered between a frame's composition and its retirement is newer intent, not a failure. On the Atomic path, R1–R5 already remove the race: the frame carries its own sprite, hotspot and visibility, acceptance publishes exactly that, and retirement does no upload or show; the newer image then progresses as frame-owned or cursor-only work under R3/R9. On the Legacy adapter, a retirement-time show whose composed version has been superseded binds the newest live image and hotspot instead of hiding; it never binds bytes older than the composed version, and it hides only when the newest intent is Hidden or no image bytes exist for any version at or after the composed one. A show that cannot bind for an actual I/O error keeps P2's existing fallback. For an animated cursor, frame 0 becomes visible without waiting for a later frame to retire, and later frames keep advancing at their own delays; the visible cursor never resolves to Hidden or Software because animation outruns flip retirement. Test on both paths a newer version registered between composition and retirement (plane stays visible and shows the newer image), a burst of versions within one flip, animation at native theme delays shorter than a frame, frame 0 visible at first show, hotspot-only changes, and hide arriving during an animation (newest intent Hidden still hides).

## Non-goals

- AMD-specific scheduling suppression, one-attempt-per-pass gates, attempt-budget policy and the `scanout.rs` deadline-spin finding (P4). P3 still supplies the basic progress source and retry after a blocking event or storage-pressure release required by R9.
- Rejection-recovery keys; changes to EBUSY/EINVAL attribution; CRTC plane reassignment; quarantine; recovery-specific cursorless retry/recompose policy; legacy executor/fallback removal; the `check-layout.sh` cursor guard (P5).
- VRR, async/tearing qualification changes, or cursor properties on async commits.
- New cursor protocol behavior, changes to XFIXES or `GetCursorImage`, sprite-pool redesign, P2 capability/eligibility changes, P1 event-identity changes, or lifecycle policy beyond canceling staged frame reservations safely.

## Test requirements

**A — End state.** Every stateful case asserts intermediate ownership and final normal-completion state. Before the replacing event, the prior sprite lease remains owned; after the exact P1 event it is released, unless successful P2 R14/R22 blocking detach or R23 all-off cleanup settled it first. Failed detach retains it. At completion there is no pending primary/event association, copied render job, frame receipt awaiting retirement, staged cursor reservation, duplicate accepted user, accepted cursor user without an owner, or live cursor allocation after pool teardown. Canceled frames leave no receipt or event obligation. Verify prepared/accepted counts for same-binding acceptance and `A → A → B`. Reservation-corruption or post-acceptance settlement-fault coverage must use an injectable transaction boundary or an explicitly permitted boundary test; direct lease mutation is not Backend coverage. Do not clear ownership maps or destroy a fixture to manufacture a settled result.

**B — Backend-driven production paths.** Install the recording atomic executor, sprite-buffer ledger, P1 device-qualified event injector and required topology, then advance through `Backend` entries or `core_loop::run_core` (including composition, direct Present, copied render completion, page-flip readiness, cursor requests and output state). Do not call internal submit/accept/retire or lease methods to simulate a production path. Pure scene-plan, receipt and request-diff boundary tests may call pure functions directly, clearly label that boundary, and do not replace Backend coverage.
